# Closed Artist Pilot

[#17](https://github.com/trmosala/CookieJar/issues/17) is **blocked by #16**. This is a proposed planning template, not an executed pilot. No participants, dates, owners, distribution, consent or sign-off are claimed.

## Proposed Plan

| Item | Proposal requiring approval |
| --- | --- |
| Duration | 10 working days after entry gates pass; actual start/end dates unassigned |
| Cohort | Six consenting internal artists: two motion designers, two compositors, two technical artists; names and backups to be assigned privately |
| Environment coverage | Only exact certified entries from compatibility.json; allocate at least two participants per approved OS family, with additional testers if needed to cover every certified storage/architecture combination |
| Projects | Approved synthetic/internal 15-30 second motion-design, layered compositing and mixed-footage projects; include text/shapes, expressions, built-in and licensed third-party effects, alpha capture, image sequences and long renders |
| Tasks | Each artist completes at least three guided sessions and one independent workflow; pairing/binding/inspection/building/animation/effects/imports/capture/checkpoints/raw scripting/rendering/restart recovery/diagnostics/update mismatch all represented |
| Proposed success threshold | At least 95% successful supported task attempts (record numerator/denominator and typed safe refusals separately); 100% security/recovery gate scenarios pass; zero unresolved data-loss/security/S0/S1 defects; every blocking defect verified resolved on affected environments |
| Qualitative measure | At least five of six artists rate workflow clarity and recoverability 4/5 or better; report limitations rather than suppressing unsuccessful tasks |
| Stop rule | Any data loss, privacy leak, unauthorized execution or unrecoverable mutation stops distribution and triggers owner-led incident/rollback review |

## Entry Gates

- Name real pilot lead, engineering lead, QA matrix owner, security/privacy approver, release signer and support/on-call owner; assign actual dates.
- Obtain participant consent, project approval and metadata retention/deletion policy before collecting anything.
- Certify all assigned environments and supply approved signed **non-production** CookieMonster and ZXP builds; record versions, hashes, trusted publisher and install/update/rollback channel.
- Resolve release-blocking dependencies and confirm training, support escalation, recovery drill and clean removal instructions.
- For 0.2.0, select explicit script exercises with exact-source approval and verified checkpoints. The previous Session raw-enable gate is retired. Requalify script behavior and partial-failure recovery before pilot use.

## Privacy And Defects

Collect only approved metadata diagnostics (versions, negotiated capabilities, redacted event codes, timings, hashes, storage modes, job states) and explicit participant reports. No automatic collection of frames, projects, checkpoints, prompts, assets, credentials, pairing codes or raw JSX. Participants review reports for accidental client content before sending. Restrict access to named support/QA owners; retention and deletion dates require privacy approval. Ordinary Session audit data must not become durable history; minimum recovery state has a separate functional lifetime.

Defect log fields: linked issue, severity, affected exact matrix IDs, minimal metadata-only reproduction, named accountable owner, containment, resolution reference, test evidence and independent verifier. All release blockers must be linked and retested across every affected environment.
